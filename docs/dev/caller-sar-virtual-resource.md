# Caller SubjectAccessReview on a virtual resource

## Problem
The agent-executor, MCP and serve-a2a gates checked `get configmaps/<caller-name>`. Any identity with ConfigMap read in the check namespace passed, including every runner ServiceAccount (ottoflow#23, criterion 3).

## Change
All three gates check `invoke callers.gate.ottoflow.nirmata.io/<name>` (`auth.CallerAPIGroup`, `auth.CallerResource`, `auth.CallerVerb`). `resourceNames` keep the three grants separate. The three chart caller ClusterRoles grant exactly that; the placeholder ConfigMaps are removed; the `ottoflow` CLI RBAC generator emits the new rule for `agentRef` steps. Failure mode is unchanged: API error or deny gives 401.

The controller still binds runner ServiceAccounts to the agent-executor-caller ClusterRole with no `bind` verb, because the chart binds the controller itself to that role.

## Why a separate group
Nothing serves `gate.ottoflow.nirmata.io` and nothing may (never add a CRD there). The verb is the custom `invoke`, so roles that read the ottoflow CRDs, even with `resources: ["*"]`, do not pass. RBAC matches apiGroups, resources and verbs each by value or `*`, so a rule grants the gate only if all three list the value or `*` (cluster-admin does); no shipped role does.

## Upgrade costs
- Hand-written Roles on `configmaps/<caller>` get 401 until re-granted with verb `invoke` on `callers.gate.ottoflow.nirmata.io`. Chart roles update in place.
- `rbac.create=false`: your own caller role must change; the controller must hold the permission it binds.
- Workflows with an explicit runner ServiceAccount skip the controller-made binding; RBAC generated by an older `ottoflow` CLI must be regenerated.
- Images are not rolled together. Until a server runs the new image, callers holding only the new chart role are denied. agent-executor and MCP (controller) roll with the Helm release. serve-a2a pods roll only when the controller re-upserts the Agent (controller start or within 10 minutes), and a pinned image tag keeps the old check indefinitely.

## Testing
`kubectl auth can-i` cannot test an unserved resource. Use a raw SubjectAccessReview with `kubectl create -f`.

## Residual unknown
Clusters with an authorization webhook ahead of RBAC (some managed offerings): behaviour for an unserved resource is unverified.
